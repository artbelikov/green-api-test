- **D23** (T3 decisions) — `receiveNotification` facade return type changed from `envelope | null` to `{receiptId, body} | null` (`ReceivedNotification`): the ack contract needs the receiptId, and the engine is built on the facades (no raw gateway calls), so the receipt must flow through. Engine correctness anchored on the saved contract (`ReceiveNotification.md`): the queue is FIFO and an un-acked notification is redelivered on the next poll — therefore the loop must drain (apply + ack) before re-polling, which also means the loop awaits subscribers before `deleteNotification` (reducers stay synchronous). 403 treated like 401 as session-invalidating, matching `mapConnectError`. Unknown/non-text notifications are acked + skipped (logging only) — otherwise the FIFO queue would livelock on a permanently-unacked head. Hidden-tab dispatch throttles to ≤1 flush per interval (1s) with instant flush on `visibilitychange`; ack still happens after apply inside the flush, so at-least-once ordering holds. `stop()` drops queued notifications on purpose (server redelivers; reducers must be idempotent by `idMessage`). Lifecycle ops serialize on one internal chain so StrictMode double-mount and rapid disconnect→reconnect can never overlap two loops.
- **D24** (T3 gotcha) — Microtask-based `settle()` helpers (N × `await Promise.resolve()`) interleave with the engine's longer promise chains instead of draining them — assertions after manual scheduler flushes must use `vi.waitFor` on observable state (see notification-engine tests). Also: the drain-before-repoll barrier means hidden-mode flushes process at most one notification per interval in practice (each admit blocks the loop until flushed); the queue+timer machinery stays for correctness, not batching.
- **D25** (T4 contract change) — `mapNotification` message events now carry `chatFallback: NotificationChatFallback | null` (engine passes it through untouched): the sync layer needs the `senderData`-derived display name to upsert unknown chats, and engine events are the only channel that still has the raw envelope context. Status events stay lean. Tests asserting full message-event shapes were updated accordingly.
- **D26** (T4 store design) — `entities/messages` is the source of truth for message data; `entities/chats` holds display state (name/preview/unread/active) and is updated ONLY through explicit calls from the composition root — `app/providers/chat-stores.ts` (engine events), `features/send-message` (send reconcile/fail mirror), `features/open-chat` (post-hydrate preview mirror) — so no entity-to-entity imports exist (FSD). Unread correctness rides on message-store dedupe: a redelivered notification produces no new message → no double unread. Chat summaries keep one sorted `summaries` array (lastActivity desc, id-asc tiebreak) instead of an id→summary map. `name` enrichment only overwrites *derived* names (name === id or name === phone), never contact-resolved ones. Message status escalation ranks `pending<sent<delivered<read` and `failed` overrides all (server authority).
