Engine correctness anchored on the saved contract (`ReceiveNotification.md`): the queue is FIFO and an un-acked notification is redelivered on the next poll — therefore the loop must drain (apply + ack) before re-polling, which also means the loop awaits subscribers before `deleteNotification` (reducers stay synchronous). 403 treated like 401 as session-invalidating, matching `mapConnectError`. Unknown/non-text notifications are acked + skipped (logging only) — otherwise the FIFO queue would livelock on a permanently-unacked head. Hidden-tab dispatch throttles to ≤1 flush per interval (1s) with instant flush on `visibilitychange`; ack still happens after apply inside the flush, so at-least-once ordering holds. `stop()` drops queued notifications on purpose (server redelivers; reducers must be idempotent by `idMessage`). Lifecycle ops serialize on one internal chain so StrictMode double-mount and rapid disconnect→reconnect can never overlap two loops.
- **D24** (T3 gotcha) — Microtask-based `settle()` helpers (N × `await Promise.resolve()`) interleave with the engine's longer promise chains instead of draining them — assertions after manual scheduler flushes must use `vi.waitFor` on observable state (see notification-engine tests). Also: the drain-before-repoll barrier means hidden-mode flushes process at most one notification per interval in practice (each admit blocks the loop until flushed); the queue+timer machinery stays for correctness, not batching.
